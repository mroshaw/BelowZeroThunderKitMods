# Reference Asset Importer

## Summary

`ReferenceAssetImporterWindow` is a Unity Editor tool for importing assets from an AssetRipper export of Subnautica: Below Zero. It copies a selected asset into the Unity project together with its recursive asset dependencies, preserves the GUIDs generated by AssetRipper, and reconnects exported script references to the corresponding types in ThunderKit's imported game assemblies.

Open the tool from **Tools > Import Reference Asset**.

By default, the selected asset and all of its dependencies retain their paths relative to the AssetRipper `Assets` directory. For example:

```text
ExportedProject/Assets/AddressableResources/Creatures/Penguin/Penguin.prefab
```

with a dependencies destination of `Assets/ImportedRefAssets` is imported as:

```text
Assets/ImportedRefAssets/AddressableResources/Creatures/Penguin/Penguin.prefab
```

The **Override Object Destination** option allows only the selected asset to be placed directly in a chosen folder. Its dependencies continue to use their corresponding AssetRipper-relative paths beneath **Dependencies Destination**. This makes it possible to gather selected prefabs from many source locations into a tidy folder such as `Assets/ImportedRefAssets/Prefabs` without flattening or reorganising their dependencies.

The window uses enhanced headings and information styling when Odin Inspector is installed and `ODIN_INSPECTOR` is defined. It falls back to the standard Unity Editor UI when Odin is unavailable.

## Using the Tool

1. Open **Tools > Import Reference Asset**.
2. Set **Export Assets Root** to the `Assets` directory of the AssetRipper export. The default is `GameFiles~/ExportedProject/Assets`.
3. Use **Source Asset** to select the asset to import. Select the asset itself, not its `.meta` file.
4. Set **Dependencies Destination** to a project-relative folder beneath `Assets`. Dependencies are copied beneath this folder while retaining their paths relative to the export root.
5. If the selected asset should be stored separately, enable **Override Object Destination** and choose **Selected Object Destination**. The selected asset is written directly into that folder using its original filename.
6. Leave **Dry Run** enabled for an initial pass. The tool discovers dependencies and reports the operations it would perform without writing files.
7. Choose whether **Overwrite Existing** should replace files already present at their calculated destinations.
8. Click **Import Asset and Dependencies**.
9. Review **Import Report** for copied, reused, skipped, or unresolved assets and scripts.
10. When the dry-run report looks correct, disable **Dry Run** and run the import again. Unity refreshes the Asset Database and highlights the imported selected asset when the operation completes.

## What Happens During an Import

### 1. Validate the paths

The tool verifies that:

- the AssetRipper export root exists;
- the selected source is an asset file inside that root;
- the source is not a `.meta` file; and
- every project destination is beneath `Assets`.

### 2. Index the AssetRipper export

Every `.meta` file beneath the export root is scanned to build a map from AssetRipper GUID to exported asset path. This allows serialized GUID references to be resolved without importing the entire export.

### 3. Index game scripts

The DLLs beneath `Packages/SubnauticaZero` are inspected for `MonoScript` assets. Their full and short type names are indexed so exported scripts can be matched to the actual game types supplied by ThunderKit.

### 4. Discover recursive dependencies

The selected asset is scanned for serialized GUID references. Resolved non-script assets are queued and scanned in turn until the complete dependency closure has been discovered. References found in both assets and their `.meta` files are included.

Only Unity text-serialized asset formats can be scanned for references. Binary assets can still be copied when another serialized asset refers to them.

### 5. Resolve script references

AssetRipper exports game scripts as `.cs` files with their own GUIDs. The importer matches those scripts by namespace and type name to `MonoScript` entries in the imported game DLLs. During copying, matching `m_Script` references are rewritten to use the DLL asset GUID and local file ID expected by Unity.

Unmatched scripts are listed as `UNRESOLVED SCRIPT` entries in the report.

### 6. Calculate destinations

Dependencies are assigned a destination made from **Dependencies Destination** plus their path relative to the AssetRipper export root.

The selected asset normally follows the same rule. When **Override Object Destination** is enabled, only that asset is assigned to **Selected Object Destination** plus its filename.

If Unity already knows an asset with the same GUID at another project path, the existing asset is reused rather than creating a duplicate GUID. This is reported as `REUSED`.

### 7. Copy or report

In a dry run, no directories or files are created; the planned destinations are reported as `WOULD COPY`.

During a real import, destination directories are created, assets and `.meta` files are copied, and script references in text-serialized assets are rewritten. Existing destination files are skipped when **Overwrite Existing** is disabled.

### 8. Refresh Unity

After a real import, the Asset Database is refreshed synchronously. The selected imported asset is then loaded from its calculated destination and highlighted in the Project window.

## Long Windows Paths

AssetRipper exports can contain deeply nested directories that exceed the legacy Windows path limits used by Unity 2019's Mono runtime. The importer switches to Windows extended-length paths and native directory creation when necessary. This support should be retained: ordinary file operations can otherwise fail even though the source asset is valid and visible in Windows.
